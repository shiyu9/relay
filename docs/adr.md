# ADR（設計判断の記録）

- 2026-07-22 セッション記録は「日記（diary/、時系列・引き継ぎ）」と「ナレッジ（knowledge/、永続知見）」の2本立て。理由: 引き継ぎ資料と蒸留知見は寿命が違う。捨てた案: 日記のみ（知見が日々に埋もれる）、ナレッジのみ（時系列の引き継ぎが失われる）、knowledge/handoff.md（日記のhandoff節と重複）。
- 2026-07-22 ファイル操作はすべてPythonラッパー（relay_recorder.py）が決定的に行い、モデルは区切り付きテキストを出力するだけ。理由: 安価モデルにファイル編集を任せたところ「追記」指示でも既存エントリを上書き消失させた（実バグ）。S番号・時刻・追記をコードに移せば喪失が構造的に起きない。捨てた案: モデルにEdit/Writeを許可する方式。
- 2026-07-22 記録はSessionEndフック→デタッチ起動のheadless Claude（既定 claude-haiku-4-5、read-only）。理由: セッション終了をブロックしない・利用枠消費を最小に。捨てた案: Stop hook方式（毎ターン発火のノイズ）。
- 2026-07-22 ナレッジの統合・矛盾解決はセッション開始時に本体Claudeが行う（終了時は単純追記のみ）。理由: 判断に迷う矛盾はユーザーがその場にいる開始時にしか確認できない。ホットループで統合しないのはメモリ設計の定石とも一致。
- 2026-07-22 注入はknowledge全文＋日記直近2ファイル全文（各knowledgeファイル約80行上限、超過は開始時に剪定）。理由: context rot対策は「小さく高シグナルに保って全文注入」が最も壊れにくい。捨てた案: handoff節のみ抽出（文脈が欠ける）、索引＋随時Read（安価モデルとの相性が悪い）。
- 2026-07-22 ナレッジ項目は「1項目1事実・命令形・[日付]付き・実際の失敗/訂正由来のみ・コード/CLAUDE.md/adrから導出可能なものは書かない」。理由: 指示が多いほど遵守率が下がるため高シグナル項目だけを蓄積する（CLAUDE.mdベストプラクティス知見）。
- 2026-07-22 時刻取得はWin32 GetLocalTime直叩き（relay_common.local_now）。理由: Git Bash由来の TZ=Asia/Tokyo をWindowsのCランタイムが解釈できずUTCに落ちる実バグを踏んだ。os.environからのTZ削除ではCRTに伝わらない。
- 2026-07-25 認証は既定でANTHROPIC_API_KEYを除去しサブスク認証で実行、RELAY_KEEP_API_KEY=1で保持に切替。理由: このキーは公式仕様上サブスクより優先され（headless -p では承認プロンプトも出ず必ず使われる）、無効キーが残った環境で記録係が401で沈黙死する事故が実際に起きた（log.txt: claude exited 129）。公式が案内する回避策もunsetのみで、優先順位を変える設定は存在しない。捨てた案: オプトイン方式RELAY_CLEAR_API_KEY=1（設定を書き忘れた環境が黙って壊れる）、除去手段なし（APIキー認証のみのユーザーを壊す）。
- 2026-07-22 対象範囲は既定全プロジェクト・RELAY_SCOPEで制限、プロジェクト無効化はRELAY_DISABLED=1。理由: 公開プラグインとして特定ディレクトリ構成を仮定しない。
- 2026-08-01 「現在の未完了」を表す第3層としてプロジェクト直下に status.md を追加（日記=時系列、knowledge=永続知見に次ぐ）。理由: 未完了事項が日記のhandoff節に散らばり、注入ウィンドウ（直近2日分）から外れると次セッションに届かなくなる。公式memory toolのmultisession patternもprogress_log（時系列）とfeature_checklist（現在の状態）の2本立てを推奨。捨てた案: knowledge/status.md（前置きの「重複・矛盾・80行超過を整理」「更新は上書き」指示がナレッジ全体に掛かり、本体Claudeがstatusを勝手に剪定する余地が残る）、diary/status.md（SessionStartがdiary/をYYYY-MM-DD.mdでマッチする実装に除外条件が要る）、日記のhandoff節をstatusに一本化（過去の日記から「その時点で何が残っていたか」が読めなくなる）。
- 2026-08-01 status.mdは追記ではなく毎回上書きで維持し、内容は未完了・保留・次アクションのみ（完了済みは書かない）。旧statusをプロンプトに渡して差分更新させ、今回のセッションで触れなかった項目は残す。理由: 完了済みを溜めると日記のdoneと重複して肥大する。「今回の内容だけで再生成」にすると、無関係な作業を1セッション挟んだだけで未完了事項が全滅し、この層が解決したい問題そのものが再発する。
- 2026-08-01 ===STATUS===セクションが空のときは既存status.mdを維持し上書きしない（「未完了なし」はモデルに明示の1行を書かせて表現）。理由: 上書き層では「モデルがセクションを出し忘れた」と「本当に全部終わった」が区別できず、前者を空扱いにすると未完了事項が黙って消える。relayは既に安価モデルの上書き消失で実バグを踏んでいる（2026-07-22の項）。捨てた案: 空を「全部完了」と解釈して素直に空にする。
- 2026-08-01 status.mdの上書き競合は台帳の.statusサイドカー（最後にstatusを書いたtranscriptのmtime）で順序保証し、より古いセッションのレコーダーはstatusを書かない（日記・ナレッジは従来どおり追記する）。理由: キャッチアップは最大3本のレコーダーを同時起動し、並行ウィンドウもあるため、古いセッションが後に完走して最新のstatusを潰す事故が上書き層固有に生じる。追記層では起きなかった問題。捨てた案: 単純な後勝ち、status.md内にHTMLコメントでメタを埋め込む（注入内容にノイズが乗りユーザーが手で消せる）、ファイルロック（同時実行は防げても「古い方が後に書く」順序問題を解けない）。サイドカーが壊れている・mtimeが取れない場合はフェイルオープン（statusを書く）とし、永久に更新されない状態を避ける。書き込みはtmp+os.replaceで原子的に行う。
- 2026-08-01 status.mdの書き手はレコーダーのみとし、セッション本体のClaudeは読むだけ（前置きに明記）。理由: 書き手が1つでないと順序保証が成立しない。「ファイル操作はすべてPythonラッパーが決定的に行う」（2026-07-22の項）の一貫。
- 2026-08-01 注入順はknowledge→日記→statusで固定（statusが末尾）。理由: statusは毎セッション全書き換えされ最も変わりやすいため、末尾に置くとセッション間のプレフィックスキャッシュ共有部分が最大になる。注入内容に現在時刻・セッションID等の毎ターン変わる要素は入れない方針も継続。
- 2026-08-01 showThinkingSummaries: true は対話モードでのみ有効、という検証結果にもとづき案3（thinkingをdecisions/mistakesの根拠に使う）を実装。理由: Claude Code本体（v2.1.220）のdisplay解決関数が `if(!isNonInteractive) return showThinkingSummaries() ? "summarized" : undefined; if(outputFormat==="text"||outputFormat==="json"&&!verbose) return "omitted"` であり、-p（headless・text出力）ではフラグが参照されず常にomittedに固定される。バンドル内に「set thinking.display to "summarized" … it is still block.thinking on a thinking block」の記述があり、レコーダーが読むフィールドに中身が入ることも確認。実地でも確認済み: relay-testプロジェクトの同一entrypoint(cli)・同一バージョン(2.1.220)・同一モデル(claude-opus-5)で、フラグ未設定のセッションが非空0/空14、フラグtrueのセッションが非空2/空0となり、jsonlのblock.thinkingに実際の中身（署名付き）が入ることを確認した。プロンプト側は「中身があれば使う・空なら何も変わらない」というデータ駆動記述にして、フラグ未設定のユーザーでも動作が変わらないようにした。捨てた案: transcript集計だけで結論を出す（entrypoint別にcli 0/2645・desktop 1021/88と割れたが、settings.jsonの過去版が残っておらず当時のフラグ値を復元できないため因果を決められなかった）、claude -p での A/B 検証（上記のとおりheadlessではフラグが参照されず、両者とも空になるだけで無効な試験だった）。
- 2026-07-27 記録の保証はSessionStart側のキャッチアップが担い、SessionEndフックは「即spawn」専用に縮小（thin判定・which判定はrecorder側へ移動）。理由: ウィンドウがclaude終了と同時に閉じる構成でSessionEndフックが完走前に殺され、記録対象セッションが無痕跡で失われる実バグ（Issue #1）。実測でフックの猶予は0.7〜1.5秒だがばらつきが大きく、ログ1行も残らないケースがあるため、フック内の並べ替えだけでは保証にならない。recorderは処理済みトランスクリプトのサイズを台帳（~/.claude/relay/ledger/<project>/<session_id>）に記録し、SessionStartで「30分以上更新なし・14日以内・台帳サイズと不一致」のものへrecorderを最大3本デタッチ起動する。導入時は既存トランスクリプトを記録済みとして台帳を初期化（過去セッションが今日の日記に化けるのを防ぐ）。resume後に成長したセッションはサイズ不一致で再記録される。捨てた案: フック内の処理順変更のみ（猶予700msに対し短縮できるのは10ms程度で今回のケースを救えない）、フック先頭での即spawn＋ガード省略のみ（フック不発・spawn前死亡を救えない）。
- 2026-08-30 日記を「1 transcript = 1 エントリ」にし、台帳（`~/.claude/relay/ledger/`）と初回採用を廃止。見出しは `## S1 19:11-22:30 (124c52dd)` でセッションIDと時間帯を持ち、エントリはそのセッション自身の日付のファイルに入る。transcript が伸びたらエントリを丸ごと差し替える。理由: 未記録かどうかが日記そのものから読めるため、二重記録を防ぐ外部状態が要らなくなる。resume で伸びた transcript が同じセッションの要約を2つ生む既存の欠陥も同時に消える。エントリが自分の日付のファイルに入るので「過去数週間分が当日の日記に化ける」が起きず、初回採用の仕掛けも不要になった。捨てた案: 台帳を残す（日記と二重管理）、見出しのIDをHTMLコメントに隠す（注入内容にノイズが乗り、ユーザーが手で消せる。2026-08-01 で同じ形を却下済み）。対立した要件: 追記のみの安全性 vs 1エントリの一意性——後者を採り、緩和は「transcript が伸びたときだけ」に限定した。
- 2026-08-30 relay 側に保持期間の窓を持たない（`CATCHUP_WINDOW_DAYS` を廃止）。存在する transcript はすべて記録対象で、1回の起動につき最大3本。理由: 窓があると「上限3本を新しい順に消化すると窓の外の古い分が永久に残る」「薄いセッションが最新のまま固定されると発掘が終わらない」という穴が生じる。境界を消せば境界の問題も消える。候補は記録するたび単調に減るので、順序の取り決めも要らない。transcript 自体は Claude Code が `cleanupPeriodDays`（既定30日）で消すため、実質そこが上限になる。対立した要件: 導入直後の利用枠 vs 記録の網羅性——後者を採った（発掘した日記は直近5件の注入窓に入らないので、価値は検索用途に限る）。
- 2026-08-30 記録手段をヘッドレス `claude -p` からセッション自身のサブエージェントへ全面置換し、`relay_recorder.py` を廃止。SessionStart が手順を注入し、本体が Task で実行する。理由: 環境制約でヘッドレスモードが使えない利用者が一切記録できなかった。タイミングの変更では解けず、手段を変える必要があった。サブエージェントへのプロンプトは「<ジョブのパス> を読み、指示に従え」の1行にし、長い指示本文はファイル側に置いて本体の文脈を汚さない。捨てた案: CLI があるときだけ従来経路（経路が2本になり試験も2本分）、環境変数で選択（既定値を選び損ねた環境が黙って壊れる。2026-07-25 で同型を却下済み）。対立した要件: 起動時の待ち時間 vs CLI 非依存——後者を採った。
- 2026-08-30 SessionEnd フックは残すが、記録はせず `~/.claude/relay/ended/<sid>` に空ファイルを1つ作るだけにした。判定は「印がある（かつ transcript が印の60秒後まで） または 30分以上更新なし」。理由: 記録を SessionStart に移すと、閉じてすぐ開き直したときに直前のセッションが30分ルールで拾えず、引き継ぎが落ちる。transcript から終了を読む手は無い（実測: 終了済み307本の最終行の型は `last-prompt` 264本ほか14種類にばらけ、しかもこの型は走行中でもターンの合間に最終行になる）。印はファイル作成1回で、書けなくても30分ルールに落ちるだけなので新しい失敗経路が増えない。捨てた案: しきい値を5分に下げる（数十秒の再起動は拾えず、並行ウィンドウを走行中に要約する危険が上がる）、最新1本だけ30分ルールを外す（並行ウィンドウと区別できない）。
- 2026-08-30 `status.md`（2026-08-01 に追加）を廃止し `knowledge/current.md` を採用、あわせて `knowledge/decided.md`（見送りと再開条件）を新設。`current.md` は現在地を書く1つの節で、上書き型・行数の上限なし。理由: 実測で `status.md` は17プロジェクトで0件、ログ1600行に記録0件だった。原因は「配信されていない」ことで、`plugin.json` / `marketplace.json` を 0.3.0 のままにしたため v0.4.0 が誰にも届いていなかった。層としては同一なので名前を1つにする。行数の上限を設けないのは、imagegen `tasks.md` の `## 現在地` が399行で腐っていない一方、同ファイルの未完了一覧45件は43件が死んでいたため——腐敗の分かれ目は上書きされるかどうかで、行数でも一覧かどうかでもない。捨てた案: `status.md` を正として `current.md` を作らない、両方持つ（4層目になり重複が増える）。
- 2026-08-30 記録のサブエージェントを2回に分ける（①transcript を読んで日記とナレッジ、②transcript を読まず現在地と見送り）。剪定は③として独立させ、`knowledge/` が80行を超えたときだけ起動する。理由: 出力契約を小さく保つほど節の欠落が起きにくい。②は①の書いた日記と既存ファイルだけを見るので transcript を読み直さず安い。剪定の発火条件を Python が計算することで、前置きの「気づいたら剪定する」（状態の記述であって手順ではない）が「条件を満たしたら起動する」に変わる。捨てた案: 1回の呼び出しで5節を出させる（`status.md` が節を落とされた疑いの形）、②③の起動判定を SessionStart 時点で行う（①が何も書かなければ②が空回りし、①の追記で80行を超えても③が発火しない）。
- 2026-08-30 日記の `handoff` 節は書き続けるが注入からは外し、注入する日記は日数ではなく件数（直近5エントリ）で切る。理由: `current.md` は handoff の蒸留なので、両方注入すると「どれが最新か」を探す作業がコンテキストの中で再現する。日数で切ると、その期間に何セッションあったかで注入量が3倍変わる（実測: 直近2日分がプロジェクト間で610〜10,518字）。handoff をファイルに残すのは、過去の日記から「その時点で何が残っていたか」が読めなくなるのを避けるため（2026-08-01 で同じ理由から一本化を却下済み）。対立した要件: 重複の除去 vs 点での記録の保存——書くのは残し、注入だけ外すことで両立させた。
- 2026-08-30 Stop フックを新設し、未記録の transcript が残っているときだけ記録を促す（プロジェクト単位で30分クールダウン、公式の `stop_hook_active` ガード）。判定は SessionStart と同じ `pending_sessions()` を呼ぶ。理由: 記録がセッション自身の実行に依存するようになったため、本体が注入手順を無視すると記録が黙って落ちる。デタッチ済みプロセスが持っていた保証を埋め戻す唯一の口になる。走行中の自セッションは終了判定で自動的に外れる。
- 2026-08-30 ANTHROPIC_API_KEY の除去（2026-07-25 の項）と `RELAY_KEEP_API_KEY` を廃止。理由: relay が子プロセスの `claude` を起動しなくなり、キーを外す責任が relay の範囲から出た。**あわせて 2026-07-25 の記述自体を訂正する**——「無効キーが残ると記録係が401で沈黙死する」は誤りで、2026-08-12 に「キーは有効で実際に課金される（kuchu-saiban で約$14 の実害）」と訂正済み。危険が世界から消えたのではなく、relay が引き起こす経路が無くなっただけである。
- 2026-08-30 リリース時は `plugin.json` と `marketplace.json` の両方でバージョンを上げ、push 後に `~/.claude/plugins/installed_plugins.json` の version が実際に変わることまで確認する。理由: v0.4.0（`f0e5043`）はこの両ファイルを 0.3.0 のままにしたため `claude plugin update` が新版と認識せず、書いたコードが1か月間まったく配信されなかった。配信の成否は、配信した側ではなく受け取った側でしか確かめられない。
