# インタビュー記録: status.md 層の追加（改善案1）

対象: `docs/interviews/2026-08-01-platform-docs-improvements-request.md` の改善案1。
日付: 2026-08-01。ラウンド数: 3。

## 背景

relay は日記（時系列）と knowledge（永続知見）の2層で、「現在の状態」を1枚で表す層がない。
未完了事項は日記の `handoff` 節に散らばるため、SessionStart の注入ウィンドウ（直近2日分）から
外れると次セッションに届かなくなる。公式 memory tool の multisession pattern
（progress_log＝時系列 と feature_checklist＝現在の状態 の2本立て）に倣い、
上書き維持される第3層を足す。

## ラウンド1

観点: ①入力の異常系（永続化ファイルの上書き喪失）、④不変条件（既存の注入・剪定指示との衝突）、
⑤解釈の言い直し（「現在の状態」の粒度）、⑥スコープ外（handoff との重複）。

| # | 質問 | 回答 | 分類 |
|---|---|---|---|
| 1 | status.md をどこに置くか（プロジェクト直下 / knowledge/ 配下 / diary/ 配下） | **プロジェクト直下 `status.md`** | 確定 |
| 2 | `===STATUS===` が空で返ったとき既存ファイルをどうするか | **お任せ** | 委任 |
| 3 | 書く内容の粒度（未完了のみ / 完了も残す進捗チェックリスト） | **未完了・保留・次アクションのみ** | 確定 |
| 4 | 日記の handoff 節をどうするか | **両方残す（役割を分ける）** | 確定 |

委任2の仮決め: **STATUS が空なら既存 status.md を維持し、上書きしない。**
「未完了なし」はモデルに明示的な1行を書かせて表現する。
理由: relay は過去に「安価モデルが追記指示でも既存を上書き消失させた」実バグを踏んでおり
（ADR 2026-07-22）、上書き層で同じ事故形を再現させない。空を「全部完了した」と解釈すると
モデルがセクションを出し忘れただけのケースと区別できない。

## ラウンド2

観点: ③状態と順序（同時実行・二重実行）、②境界（上限）、①異常系（前回項目の消失）。

|---|---|---|---|
| 5 | 前回の未完了項目が今回のセッションで一切触れられなかったら | **そのまま残す（解決の証拠があるときだけ消す）** | 確定 |
| 6 | 複数レコーダーが同時に走るときの上書き競合 | **新しいセッションが勝つ（順序保証する）** | 確定 |
| 7 | 薄いセッション / NOTHING_TO_RECORD のときの status | **据え置き（何もしない）** | 確定 |

質問6は、キャッチアップが最大3本のレコーダーを同時起動し、かつユーザーが並行ウィンドウを
常用しているため実際に起きる。日記は追記なので共存するが、status は上書きなので
「古いセッションが後に完走して最新を潰す」事故が上書き層固有のリスクとして生じる。

## 「なし」と判断した観点

- ②境界のうち「0件・1件」: 注入側は既存の「内容が空ならセクションを出さない」パターンで自動的に処理される。
- ①異常系のうち「非ASCII」: 既存の `force_utf8` と `encoding="utf-8"` 統一で対応済み。試験バッテリーで担保。
- ⑤解釈のうち「信頼境界・エスケープ」: status.md は素の Markdown で、HTML/クエリに埋め込まれない。
- ⑥スコープ外: status.md を git 管理するかはユーザーのプロジェクト側の判断。プラグインは `.gitignore` に触らない。

## 要件整合チェック

**問題なし（矛盾なし）。**

- 矛盾: なし。「未触項目は残す」（回答5）と「STATUS 空なら既存維持」（委任2の仮決め）は
  どちらも保守側に倒れており整合する。「本体は読むだけ」（回答9）は「順序保証」（回答6）の
  前提を満たす（書き手が1つならサイドカーによる順序判定が成立する）。
- 抜け: 委任1件（回答2）は仮決めを明記済み。保留はなし。
- 穴: 確定仕様の組み合わせから新たな未定義は生じていない。
  - 「未完了なし」の表現は、モデルが1行書く → 通常の上書き経路で反映されるため整合。
  - 順序保証サイドカーが壊れている/存在しない場合はフェイルオープン（書く）。
    そうしないと status が永久に更新されなくなる。外から見えない内部都合なので委任枠で仮決め。
  - `===STATUS===` が無い旧形式の出力は、`DIARY` 必須のまま `STATUS` を optional にすることで
    後方互換を保つ。

## 技術選定

**標準ライブラリのみ（`pathlib` / `os` / `re`）。外部依存なし＝脆弱性チェック対象なし。**

順序保証（「新しいセッションが勝つ」）の実現手段:

| 案 | 内容 | 判定 |
|---|---|---|
| **採用** | 台帳 `~/.claude/relay/ledger/<project>/.status` に「最後に status を書いた transcript の mtime」を保存し、より古い mtime のレコーダーは status を書かない | 既存の `recorded_size`/`mark_recorded` と同じ思想で新概念を持ち込まない。session_id は UUID なので先頭ドットのファイル名と衝突しない |
| 捨てた | status.md 内に HTML コメントでメタを埋め込む | 注入内容にノイズが乗る。ユーザーが手で消せる |
| 捨てた | ファイルロック（msvcrt/fcntl） | 同時実行は防げても「古い方が後に書く」順序問題を解けない。プラットフォーム差も出る |

書き込みは一時ファイル＋`os.replace` で原子的に置換（途中失敗で壊れた status.md を残さない）。

既知の限界: サイドカーの read→write は原子的でないため、複数レコーダーが同一ミリ秒帯で
最終書き込みを行うと理論上は競合しうる。ただし窓は数ミリ秒で、headless 呼び出しの数十秒に対して
無視できる。影響も「次のセッションまで status が古いまま」に留まる。

## 委任された点と仮決め

| 論点 | 仮決め |
|---|---|
| `===STATUS===` が空のときの挙動 | 既存 status.md を維持し上書きしない。「未完了なし」はモデルに1行書かせる |
| サイドカーが壊れている/読めないとき | フェイルオープン（status を書く）。永久に更新されない状態を避ける |
| transcript の mtime が取得できないとき | status は書くがサイドカーは更新しない（`mark_recorded` が size 取得失敗時に書かないのと同じ扱い） |

## 保留された点

なし。
