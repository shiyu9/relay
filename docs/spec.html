    第 3 章システム概要

    3.1 概要

    relay は、Claude Code のセッションが終わるたびに会話ログを読んで要約し、次のセッションの開始時にその要約を注入するプラグインである。人が引き継ぎを書かなくても、次のセッションが前回の続きから始められる状態を保つ。

    できること。 会話ログから日記・ナレッジ・現在地・見送りを書き起こす。完了したタスクを tasks.md から消す。起動時にそれらを注入する。記録はセッション自身のサブエージェントが行うため、ヘッドレスの claude CLI を必要としない。

    やらないこと。 セッションの途中で口を出さない。タスクを追加しない（消すだけ）。会話ログを書き換えない。プロジェクトの構成を仮定しない。

    書き込みはすべて Python が決定的に行う。 記録係は区切り付きのテキストを一時ファイルへ出すだけで、日記もナレッジも直接触らない。安価なモデルに追記を任せて既存エントリを消失させた事故が実際にあったため（D-02）。

    適用の範囲は第 11 章、決定の理由は第 12 章に分けて書く。

    3.2 適用場面

    P-01次のセッションを、前回までの記録から始める

    起動時に引き継ぎを注入し、記録し残したセッションがあればその手順も渡す。P-02 を忘れた場合の受け皿がここにあたる。

    処理の流れ図 3-1

    起動時の記録は 1 回につき 3 本まで。残りは次の起動に回る（N-08）。

    P-02セッションを閉じる前に、そのセッション自身を記録に残す

    利用者が「記録して」「店じまいして」と頼むと /relay:record が走る。起動時の記録と違い、いま動いているセッション自身も対象に入る——通常の判定は「終了印がある、または 30 分以上更新なし」なので、走行中のセッションは決して対象にならないため。自分を見分けるために、スキルは毎回新しいトークンを作ってコマンドに載せる。ツール呼び出しは実行される前に transcript へ書かれるので、スクリプトは自分が書き込まれているファイルを名指しできる。

    処理の流れ図 3-2

    特定できたセッションだけが終了判定を免除される。ほかの transcript は通常の判定のまま扱われるので、別のウィンドウで進行中のセッションが途中で要約されることはない（N-03）。

    P-03セッションが終わった事実を残す

    「静かなだけ」と「終わった」を次の起動が区別できるようにする。これが無いと 30 分の無更新を待つしかなく、閉じてすぐ開き直した場合に直前のセッションが引き継がれない。

    処理の流れ図 3-3

    印が書けなくても 30 分の無更新で拾えるため、これは最適化であって依存ではない（D-06）。

    第 4 章システム構成

    4.1 構成要素

    起動フック新規起動と /clear のときに走り、引き継ぎと記録手順を標準出力へ出す
    終了フックセッションが閉じるときに走り、終了印を 1 つ置く
    記録スキル利用者が明示的に頼んだときだけ走る /relay:record
    検出日記と transcript を突き合わせ、記録すべきセッションを決める
    ジョブ生成記録係への指示書を書き出し、それを呼ぶ手順を組み立てる
    反映受け皿のテキストを読み、日記・ナレッジ・現在地・タスクへ決定的に書き込む
    記録係Claude Code のサブエージェント。transcript を読んで区切り付きテキストを書き出す
    プロジェクトの記録日記・ナレッジ・現在地・見送り・タスク
    作業領域~/.claude/relay/ 配下の epoch・終了印・指示書・受け皿・ログ

    4.2 要素間の関係

    要素間の関係図 4-1

    検出は起動フックと記録スキルの両方から同じ関数として呼ばれる。2 つの入口が「何が未記録か」で食い違うことはない（D-07）。

    4.3 動作環境

    実行系Python 3（標準ライブラリのみ。外部依存なし）
    必須の外部コマンドなし。ヘッドレスの claude CLI を必要としない
    検証済みの OSWindows 11。macOS・Linux 向けの記述はコードにあるが未検証（X-05）
    記録係のモデル既定 claude-haiku-4-5。RELAY_MODEL で変更できる
    配置Claude Code のプラグインとして ~/.claude/plugins/ 配下に置かれる
    設定環境変数 RELAY_SCOPE RELAY_DISABLED RELAY_MODEL RELAY_MIN_USER_MSGS RELAY_EPOCH

    第 12 章設計判断

    ID決定理由
    D-01日記とナレッジを分ける引き継ぎ資料と蒸留知見は寿命が違う。日記だけだと知見が日々に埋もれ、ナレッジだけだと時系列の引き継ぎが失われる
    D-02ファイルへの書き込みをすべて Python が行う安価なモデルに「追記」を指示したところ、既存エントリを上書きして消した実バグがある。番号・時刻・挿入位置をコードへ移せば、喪失が構造的に起きない
    D-03記録をサブエージェントで行うヘッドレスの claude CLI が使えない環境では、それ以前の方式だと記録が一切残らなかった。タイミングの調整では解けず、手段を変える必要があった
    D-041 transcript = 1 日記エントリ未記録かどうかが日記そのものから読めるので、二重記録を防ぐ外部の台帳が要らない。再開で伸びた transcript が同じセッションの要約を 2 つ生む欠陥も同時に消える
    D-05導入時に一度だけ線を引く線が動くと「昨日は内側、今日は外側」の取りこぼしが生まれる。一度きりの線には外側が無い。導入のたびに全履歴の要約代を払う問題も同時に解く
    D-06終了フックを印だけにするウィンドウが claude と同時に閉じる構成では、フックが完走前に殺される（ログ 1 行すら残らない例を観測）。空ファイル 1 つなら失敗しても 30 分の無更新で拾える
    D-07検出を 1 か所に持つ起動フックと記録スキルが同じ関数を呼ぶので、2 つの入口が「何が未記録か」で食い違わない
    D-08統合で項目を削除しない行数の上限に合わせて削ると、一次情報が失われる。80 行は「そこが育った」という合図として使い、移設の候補を挙げるだけにする
    D-09Stop フックを撤去する毎ターン全 transcript を走査していた（実測 70〜250ms）。分類器に拒否されるとセッション内で解決できないまま 30 分おきに促しが出続けた。猶予と間隔の 2 つの定数に暗黙の順序依存もあった
    D-10記録を手動と自動の 2 段にする手動が基本、忘れたら次の起動が拾う。手動にしかできないのは「いま動いているセッション自身の記録」で、それが手動の存在理由になっている
    D-11自分の特定を fail-closed にする一致が 2 本のとき新しい方を採ると、別のウィンドウで進行中のセッションを途中で要約することになる。曖昧なら記録しない方が、打ち直し 1 回で済むぶん安い
